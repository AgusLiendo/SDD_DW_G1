# Easa — Base transaccional PostgreSQL

**Fuente:** DER-Optimizado.png proporcionado mediante Google Drive, contrastado con la entrega 1 del PPAI del Grupo 1. Este proyecto **no crea el Data Warehouse**, sino su base operacional de origen para el futuro ETL.

## Archivos

- `00_crear_base.sql`: crea una base de datos vacía `easa_oltp`.
- `easa_oltp_schema.sql`: crea las **44 tablas** del DER, sus relaciones, restricciones e índices.
- `02_catalogos_opcionales.sql`: carga ciudades, seis sucursales, tipos de cliente, medios de pago, estados y tipos de movimiento, basados en la descripción escrita de la entrega 1.
- `easa_oltp_psql.sql`: script instalador para la consola `psql` que invoca los otros archivos con `\ir`.
- `easa_oltp_completo_psql.sql`: **un solo archivo monolítico** que crea base y tablas, ejecutable desde `psql` (no necesita los demás archivos).

## Ejecución desde pgAdmin

1. Conectarse a la base `postgres` y ejecutar `00_crear_base.sql` (**sin** transacción explícita).
2. Actualizar el árbol de bases y abrir **Query Tool** sobre `easa_oltp`.
3. Ejecutar `easa_oltp_schema.sql`.
4. Opcionalmente ejecutar `02_catalogos_opcionales.sql`.

> No ejecutar `easa_oltp_psql.sql` desde pgAdmin: sus líneas con `\` son comandos de la consola `psql`, no SQL estándar.

## Ejecución desde psql

Desde la carpeta con los scripts (o ejecutar `easa_oltp_completo_psql.sql` si se desea un único archivo):

```bash
psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f easa_oltp_psql.sql
```

O por separado:

```bash
psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f 00_crear_base.sql
psql -U postgres -d easa_oltp -v ON_ERROR_STOP=1 -f easa_oltp_schema.sql
psql -U postgres -d easa_oltp -v ON_ERROR_STOP=1 -f 02_catalogos_opcionales.sql
```

## Convenciones adoptadas

- Se conservaron las entidades del DER pero se utilizaron nombres de tablas y columnas `snake_case`: por ejemplo, `DetalleVenta` → `detalle_venta`, `precioUnitarioHistorico` → `precio_unitario_historico`.
- Las PK son `BIGINT GENERATED BY DEFAULT AS IDENTITY`; los importes son `NUMERIC(14,2)` o `NUMERIC(14,4)` para los precios, y las cantidades son `NUMERIC(16,3)` para admitir unidades fraccionarias.
- El recuadro **FactorComplejidad** se representa con un `CHECK` que admite 1, 1.5 y 2, porque el DER lo expone como enumeración de valores, no como entidad con PK.
- El campo `Usuario.contraseña` se representa como `contrasena_hash` y no debe guardar contraseñas en texto plano.
- `MovimientoStock` y `AjusteStock` incluyen una restricción para que cada registro afecte a **exactamente uno** entre `producto_sucursal` e `insumo_sucursal`.
- Se añaden validaciones de consistencia para evitar asociar detalles de pago con compras de otro proveedor, detalles de cobro con ventas de otro cliente y repartos con detalles de otra instancia de producción.
- Algunas reglas de negocio **no pueden inferirse completamente de las cardinalidades del DER**. No se inventaron campos como `sucursal_id` en `venta` ni en `compra`: la sucursal se obtiene a partir de los detalles.

## Validaciones que requieren lógica adicional

- Verificar que la promoción elegida para una línea de venta corresponda al producto, tipo de cliente y vigencia.
- Garantizar que una producción solo ocurra en sucursales con `tiene_planta = TRUE` y que el empleado posea un rol apropiado.
- Impedir que los repartos acumulados excedan lo producido y definir si el destino de la planta necesita reparto explícito.
- Evitar intervalos de vigencia **solapados** en `precio_producto` y `precio_insumo`; el esquema comprueba fechas válidas, pero no impone exclusión de rangos.
- Controlar saldo acumulado: que pagos no excedan compras y cobros no excedan ventas, y mantener `estado` correctamente actualizado.
- Mantener saldos `stock_actual` y sus `movimiento_stock` sincronizados; el esquema guarda los registros, pero no implementa actualización automática.
- El catálogo `estado` se comparte entre compra, venta y cheque, como en el DER: la FK no verifica que el `ambito` asociado sea el correcto.

## Consultas de comprobación

```sql
-- Cantidad de tablas del esquema:
SELECT COUNT(*) AS tablas
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE';

-- Inventario con sucursal para la consulta 1 del PPAI:
SELECT s.nombre AS sucursal, p.nombre AS producto,
       ps.stock_actual, ps.stock_minimo
FROM producto_sucursal ps
JOIN sucursal s ON s.id = ps.sucursal_id
JOIN producto p ON p.id = ps.producto_id
ORDER BY s.nombre, p.nombre;

-- Datos de ventas disponibles para la extracción ETL:
SELECT v.id, v.fecha_hora, tc.nombre AS tipo_cliente,
       s.nombre AS sucursal, p.nombre AS producto,
       dv.cantidad, dv.precio_unitario_historico,
       dv.promocion_id
FROM detalle_venta dv
JOIN venta v ON v.id = dv.venta_id
JOIN cliente c ON c.id = v.cliente_id
JOIN tipo_cliente tc ON tc.id = c.tipo_cliente_id
JOIN producto_sucursal ps ON ps.id = dv.producto_sucursal_id
JOIN producto p ON p.id = ps.producto_id
JOIN sucursal s ON s.id = ps.sucursal_id;
```

**Importante:** el esquema define la estructura pero no contiene datos transaccionales de prueba; el catálogo opcional tampoco crea ventas, compras ni producciones ficticias. Para demostrar cubos OLAP en Metabase, será necesario cargar datos operacionales de varios períodos antes de ejecutar KNIME.
